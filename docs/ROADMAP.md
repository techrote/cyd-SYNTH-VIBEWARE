# Programme roadmap

Programme #1 is the live milestone ledger. Milestones are evidence gates, not dates or promises. Creative workers can progress native cores concurrently with platform development; avoid architecture-induced serialization.

| Milestone | Scope | Exit criteria |
|---|---|---|
| M0 bootstrap | Charter, worker ownership, hardware and qualification contracts, four founding issues | Docs on main; executable next tasks; status explicit |
| M1 foundation | One minimal reference app, real portable core, touch/render/audio adapter and evaluator | Actual native execution, ESP32 compile/link, real PCM/frames, timing instrumentation, Windows extraction, no false physical claims |
| M2 founding instruments | PHASESPACE, CHRONOGRID, XENOBIO, PHOSPHOR | Each has distinct playable native and CYD build, controls/presets/scenes and independent evidence |
| M3 refinement | Performance budgets, interaction, physical evaluation package | Repeatable stress; useful presets; target identity, recovery and owner-review candidate; actual physical result separately |
| M4 expansion | Choose next instruments based on catalogue gaps and creative results | First instruments not abandoned; evidence-based selection; no speculative modular framework |
| M5 connectivity | Optional CYD clusters/FM-1/MIDI/OSC, profiling | Transport capability verified; reconnect, bounded queues, panic, offline fallback; separate profile |
| M6 collection | Shared launcher and catalogue | Measured flash/RAM fits, isolation/reset between apps, persistence migration, extracted evaluator; individual builds retained |

## Critical path and decisions

PLATFORM and QA establish the smallest reliable common path. Creative lanes begin with independent cores and local adapters, then align at a demonstrated contract. Prioritize interface stability and early Windows owner evaluator. No full SDK, unified launcher, external transport, PSRAM or physical board dependency is required to start. If target work blocks, progress portable core, native interaction and reproducible diagnostics; do not call host a target run.

M3 owner review can occur per instrument rather than waiting for entire collection. All implementation PRs stay Draft/HOLD until independently qualified and owner-approved. QA tracks integration order and conflicts; no automatic merge. M4/M5 optional roster growth is based on actual backlog; if queue grows slow creative starts and repair existing packages. No artificial waiting or deadline promises.
